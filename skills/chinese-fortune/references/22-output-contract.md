# 解读输出契约：事实、条款、条件与纠错

所有方法在输出个人解读前必须遵循本篇。旧参考中的吉凶词、性格词和命例只作传统材料，不是可直接套到用户身上的结论；本篇优先规定其使用方式。

## 本次采用的体系与时间

八字默认采用《子平真诠》的月令格局主线；其他四书补充对应问题，分歧单独说明。用 `classical_search.py --list-books` 确认固定版本和收录状态，用 `classical_search.py` 获取原文、段落 ID 和上下文。全文已收录、转录已核、影像已校、规则适用是四项不同的事实。

问题依赖“现在”时先获取当前所在地时间，一次取得、同请求复用；纯原局、术语解释和明确参考年份无需为现居地停下。出生资料始终按出生地和历史时区处理；用户明确问的历史或未来时间优先。具体输入规则见 [输入与时间](00-intake.md)。

## 1. 四层内容分开

| 层次 | 可以说什么 | 不可以跨越什么 |
|---|---|---|
| 盘面事实 | 已核算的干支、星曜、宫位、历法口径 | 未知时辰不擅填；不能声称已经验证现实命运 |
| 传统解释 | 指定版本、条款和条件下的解释 | 注文不冒充正文，候选不冒充定论 |
| 现实假设 | 明确标记的类比或待验证问题 | 不能从十神直接断职业、配偶行为或疾病 |
| 实际建议 | 根据用户已提供的现实情况提出可行建议 | 不能包装成古籍必然要求或保证结果 |

古籍真实性、传统规则适用性与现实预测效度分别处理。旺衰分数是工程启发式，不是发生概率。

## 2. 输出前核查

每条主判断记录：结论性质、盘面字段及值、来源 ID、规则 ID、成立条件、例外、适用时间范围。条件采用 `met / not_met / unknown`；状态采用 `supported / needs_review / disputed / insufficient`。

八字完整 JSON schema 2.1：`chart_facts` 是盘面，`observed_structure` 是透藏位置，`rule_assessment` 是相关路径三态条件，`geju_review` 是成败救应和变化观察，`evidence_bundle` 是完整原文及例外，`reading_support` 是初始事实。Skill 默认调用 `--view compact`，用条件引用与 `evidence_index` 去重；解释前按段号取完整上下文，同一请求已取得的段落复用。详见 [5.10 迁移](../docs/MIGRATION-5.10.md)。没有 `yong_shen`、`ge_ju` 或 `source_passages`，不为取这些旧键再调用诊断工具。

证据组按书、章、段去重。已有段落可直接使用；只有所问范围尚未覆盖才补检索。逐条核完相关解释条件，资料够用就回答，不把所有 `unknown` 原样交给用户。某条前提不满足只能排除该路径，不能说全盘无用或所有解释都不成立。

有完整条款且成立条件均已核实，才可形成有条件的传统解释；仍应说明例外与范围。未核规则不得凭模型记忆补成“某书云”。候选交集、多个方法结论相似，不是独立验证。

使用 `scripts/reading_support.py` 核查证据记录。可在内存调用 `review_claims(chart, packet)`；也可用 `--stdin` 输入 `{"chart": ..., "packet": ...}`，避免为了校验生辰额外落盘。它检查记录结构、盘面引用和原文，并重新计算新八家规则中可计算的条件，防止模型把明显不符的条件填为成立。解释条件另需 `condition_evidence`：说明理由、实际盘面路径和值、所用段落 ID；来源限本家条款、例外、共同依赖及本盘调候证据，不能拿另一书的真实标题充数。它无法认证推理文字是否正确，仍须逐句检查最终正文。

紫微、六爻各有四条独立基础条款，排盘的 `reading_support.method_rules` 返回相应盘面与条件；完整条款可通过 `method_rules.py --method ziwei|liuyao` 查询，应用记录用该工具核查。未注册的解释仍须单独定位，不能借八字的来源 ID。没有可定位的条款时，可以说明传统概念，不能据此确认具体个人事件。

未来时段入口的 `traditional_observations` 使用两种独立的行运例式，计算时核实出生字段、实际大运及原文哈希；其 `structural_example_matched` 只代表例式结构命中。它们不属于原局25条路径，不传给 `reading_support.py` 冒充原局规则，也不把该状态改写成整体运势良好。临时补查出的其他解释依专用流程记录、逐句复核；未注册不等于自动通过。

## 3. 古籍证据

基础证据与八家条件分别由注册表和规则库维护，通过工具访问，不直接加载大 JSON。新增八家规则以稳定段落 ID 关联全文。版本、卷章、正文/注文层次和核验状态随证据组返回。

- `transcription_checked`：仅核网络转录，不能称已核原刻本。
- `facsimile_checked`：须实际核过对应页影像才能使用。
- `pending`：只作查找线索，不可直接引号引用或用于确认个人判断。
- 原文与项目归纳分开；引用只取已核原文，不拼接成新句。
- 不同版本有异文时保留版本；不因多个转录网站文字相同就算多份独立证据。
- 《子平真诠》格局用神、《滴天髓》及注本的气势解释、《穷通宝鉴》调候不强制合成一个字。先解释各自条件，冲突时列分歧，不默认调候压倒格局。同一体系内两条条款相反时的裁决顺序见 [裁决顺序](26-precedence.md)；跨体系仍然列分歧，不排序。
- 《三命通会》《渊海子平》需同样定位条款；仅列书名不能支撑判断。

调候逐格来源状态由 `tiaohou_provenance.py` 查询；相关问题的默认结果也带 `climate_review`。一般候选与附加条件分开，缺当月专段则明确缺项，不用季节总论填补。旧表候选和混合版本注记只保留作审计。资料里的科甲、刑克等古代措辞保留文化语境，不能自动翻译成现代学历、疾病或第三方行为。

## 4. 正文模板

自然白话表达见 [直接回答](27-direct-answer.md)。证据与适用条件始终决定结论强度；任何表达模板都不能扩大已核结论。默认正文约300–600字，简单问题更短。

默认回答所问，主判断不超过三条；用户要求全面解读再扩展。不要每次倾倒全部十神、神煞和年份。

采用 Caveman 的简洁与清楚原则：自然短句，一句一件事；删套话，保留原因、条件、否定和时间范围。先给白话结论，再给少量古文作依据。术语首次出现就解释，不写文言碎句。正文以理解和回答问题为准，不以压缩字数为目标。

1. 一至三句普通话直答：本题能确定什么、原因是什么、最关键的限制是什么。开头应能独立读懂，不用尚未解释的格名或“透藏、根气、救应”串成摘要。先说关系怎样起作用，再引入古籍名称；不能为通俗而改写成未经支持的性格、职业或事件。
2. 按需给四柱或命宫等核心事实；表格放在直答之后，只列影响本题的内容。用户没要求完整排盘时，不先摆出全部藏干和十神让用户自行消化。
3. 每条判断按“白话结论 → 必要盘面 → 短原文与出处 → 紧跟白话解释”写成自然段。**每一段引文后都要解释**：原文在说什么，本人的哪些具体条件与它对应，为什么支持本题判断；例外和分歧随该条说明。古文含义与现代场景解释分开，不能用另一串术语代替白话，也不能只放一个书名让人自行理解。
4. 涉及岁运时再说明本命、大运、流年的关系；没有月度依据不得给月份，没有日度依据不得给日期。
5. 一至两条基于现实情况的建议，以及补充哪项信息会改变哪条判断。

**按问题类型的骨架**（第五轮盲评的 24 项低分都在易懂度和完成度，事实与引文没有失分；`research/gpt-results-20261101/R3/LOSS-ANALYSIS.md`）：

- 近期运势、最近事业：先说这段时间指哪天到哪天；再逐层说本次算到了什么（大运、流年、月、日，各一句白话），没算到的层直说没有；然后按用户说的处境（升职、换工作、项目）各给一两条现实动作，标明是现实建议。「不能保证结果」只说一次，不能代替上面已能确定的部分。`fortune_reading.py --markdown` 的「写回答时」会给出这次的具体窗口和层次。
- 排盘、装卦、合婚关系：先给表，再用一两句教读表（哪一行是什么、动爻怎么看），然后按所问解释；额外的断法放在可选的后段。
- 格局条件、古籍出处：正文只节录与所问直接相邻的一两句，段号随附，完整段落让用户自己展开；正文、注文、版本说明分层，不把整段成格条件一次铺开。
- 五行、十神计数：用每行列数相同的 Markdown 表，不写 colspan 之类 HTML（`answer_check` 会提示）；先给计数，再说「数量缺不等于喜用」，再讲判断用到的条件。
- 每个技术条件后面跟一句读者能复述的意思，再说它不能推出什么。一个例子讲清一个关系，例外放进证据段。

短期运势与择时遵循 [个人未来时段](24-personalized-forecast.md)。周是用户的展示范围，不独立创造周运算法。年、月、日、时事实的显示精度不代表吉凶规则精度；主方法、个人字段和候选比较依据在判断前确定。个人古法首选需要已核规则确实区分候选；实际档期首选可按用户已给的现实条件产生，必须标明选择理由和日期、起止时间、时区。两类结论分别记录，不足的古法部分继续补查。通用黄历不冒充个人八字排名，多个方法相同不作概率证明。

**工具结论优先。** 工具标明不判、未接入、给不出、并列或 `first_choice` 为空的，回答照说，不补判、不排先后；干支、十神、生肖、旺衰、日期等级、大运喜忌只从工具输出取，不另写代码推算；`--markdown` 草稿末尾的「写回答时」各条必须照做（依据：`evals/v56/REPORT.md` 第 3.1 节，48 题里 16 题自行推算、事实只过 17 题）。

**不能用白话类比绕过缺失规则。** “印日适合学习核对、食伤日适合表达交付、财日适合结算、冲日多留调整余量”都是个人日期建议，并非单纯盘面事实；必须有该粒度的适用原文、本人条件和例外核查。只引《论行运》或《论用神成败救应》的总论，不能支持周内这样的分工。把断语改称“倾向”“象征”或在末尾加免责声明，仍不能通过。

这也适用于整周摘要，不能仅把逐日断语合并成“这周主题是成果落地、资源安排”。食神与财同时出现，只是关系计算；未核整盘喜忌、轻重及相关条款，就没有形成可作现代解读的传统判断。`recommendation.status=evidence_needed` 且未补得完整适用规则时，开头直接说明“出生盘和日期已核实，但现有依据还不能判断下周整体顺不顺”；随后可解释已支持的原局或长期条件，不能在结尾又给本周主题和个人活动建议。一般现实建议只依用户已给的现实条件。

例如，已算出周四甲午、甲对日主为食神，只能解释这一关系如何计算；没有核准日级条款，不能续写“所以周四适合展示”。若只能核实大运背景，就只解释该长期背景并明确它不能区分本周各日。现实建议应从用户实际档期、准备进度和任务要求得出，并说明这个现实依据，不冒称个人命理建议。

档期正文默认只列实际可开始范围、持续分钟和时区。确需解释跨时辰时，复用 `candidate_comparison.windows` 中覆盖全过程的分段，不凭开始时间手补时柱。边界按半开区间处理：例如时辰在11:00更换，一小时事件10:30开始会跨界，11:00开始则从新时辰起；不能把前者说成单一时盘、后者说成跨界。

**“未能评价”与“评价后并列”必须分开。** `evidence_needed` 表示没有足够依据比较，不能在末尾改说“术数上并列”“两天一样好”或“打不破平局”。只有同一套完整规则已核两个候选、结果确实相等，才称并列。两天现实上都有空，也不能证明传统评价相等。

完整盘面字段可放末尾附录或按需展开；未知字段明确待补。原局层面只有“变动”象征时，不能扩写成失业、离婚或某个具体事件。不得编造 80%/90% 命中率。一次说明文化参考性质即可，避免重复免责声明。

例如，讨论官的配合时，不以“官旺有根，财印不透，救应未成”起头。可先说：“按这套古法，约束的这条关系比较明确，但支持它发挥作用的条件还不齐全。下面能解释各方怎样配合，不能仅凭这个结构保证现实结果。”再逐项说明对应的盘面和条件。例句只是表达方式，盘面不支持时不得照搬。

发出前单独重读第一段：如果用户必须先知道“正官格、杂气、透干、有根、佩印、成格”才能理解，就重写这一段。即使问题本身用了格局名称，也不免除白话开头。不要把一串术语加引号或加粗后称为白话；术语及其具体排盘依据放在后文解释。

## 5. 纠错、时辰区间与一致性

禁止强制猜 3–5 件往事。用户提供的经历只作现实背景，不再当成功预测。用户更正出生资料时，先用 `scripts/birth_correction.py --stdin`（`{"before": 原资料, "after": 新资料}`）列出改了哪项、哪几柱跟着变、哪些旧结论作废（`invalidated`）、哪些柱不变（`kept_pillars`），再用新资料重新解读；回答开头照 `say` 说明更正与作废范围，最新结果以新盘为准。用户说“不对”时保留初次判断，承认不符，分别标记输入更正、计算修正、流派变更或解释修订；后者不能回改盘面事实。

时辰区间跨边界时，分别计算候选盘，优先输出共同支持的事实；不同的结论说明对时辰敏感。不能根据哪张“更像用户”就宣称出生时间已校准。同出生资料的双胞胎不能承诺用另一术数一定区分。

现实预测若需评估：事先固定问题、时间窗口、事件定义与失败标准，再隐藏结果生成判断。全部失败也须记录。命例和事后解释只能检查文本理解，不能作为现实命中率。

## 6. 术语与例子

“盘面事实”表示指定计算口径下的结果；“条件支持”表示传统规则前提已检查；“有分歧”表示规则或输入口径不同；“暂不能判”表示关键信息或条款缺失。

示范（非个人排盘）：伤官与正官并见只触发核查。《滴天髓·格局论》正文说“傷官見官果難辨，可見不可見”；还需查身强弱、财印与救应，不能直接推断事业不顺或婚姻失败。核查完成后应具体写出已满足的条件，不用空泛“可能”代替解释。

“偏弱”“偏旺”是旺衰启发式的中间等级；“透干通根”指天干显露及地支根气两项条件，不能只见其字就当条件成立。

## 7. 执行细则

以下是宿主每次回答都要遵守的具体做法，[SKILL.md](../SKILL.md) 只列要点。

### 7.1 工作流程

2. 本题依赖“现在”时才确认当前所在地的 IANA 时区：未来时段入口自行取时；其他当前时间入口先运行 `scripts/request_time.py --current-timezone <时区>`。已有 utc 时，同请求复用为 `--request-time`（JSON 入口为 `request_time`），不重复取时。古籍查询、术语解释、纯原局和明确参考年份不必为现居地卡住；只有相对时间未固定时补问；「最近」「近期」「这段时间」不补问，按 `period: "近期"`（今天到年底，剩不到一个月时算一个月）算，开头说明这是暂按的范围。用户已经给出的出生资料、历法、城市、年份和请求时间直接复用，不整表重问。
3. 出生钟表时间用出生地时区；“现在”用现居地；历史或未来问题用明确目标时间。不得给历史日期拼上当前时分。重新要求“现在再算”时重新取时，同请求跨午夜仍沿用首次时刻。
4. 解读前固定本题主方法、版本、事件定义和时间范围。逐条列明实际个人字段、成立条件、例外及本题影响；未解决的分歧明确保留，不投票、不反复起卦挑答案。同输入与方法应得同结论；相同适用条件允许同结论，不为显得个性化而改答案。确定的是依据支持的判断，不是保证现实事件发生。
5. 按路由排盘，检查 exit code 和 `ok`。多方法、多人或多步骤的问题先交付已算完的部分：工具累计耗时超过约三分钟时，先答已确认的结论，再列还没算的步骤，不让用户等到最后一无所获。失败就处理真实错误，不凭记忆补造成功结果：按 `error_class` 走 `next_step`（input 改输入、context 补时区、choice 让用户从 `candidates` 选、unsupported 如实说不支持、environment 跑 `scripts/doctor.py`、integrity 是工具自身资料断链，如实说维护问题）。成功结果的 `envelope` 汇总方法、时间约定和复现字段，复述方法或重算时以它为准。
6. 纯本命默认只调用 `scripts/bazi_reading.py --view compact --facts-out <临时目录>/bazi.json`：屏幕只出约两千字的白话草稿和文件路径，完整 JSON 存在文件里（带大运的 compact 视图可超过 40KB，直接打到屏幕会被宿主转存，多一轮读取）；需要细节时按下面的字段名到文件里查。`chart_facts` 给盘面，`rule_assessment` 给条件，`geju_review` 核成败救应与变化，`evidence_index` 给段号。`condition_refs` 指向同一 assessment 的 `conditions`；`*_refs` 指向同一 review 的同名索引表。引用或解释前按段号取完整原文及上下文；已取段落直接复用。需要全部计算细节时才以同一资料、参考年和请求时间运行 `--view full`，其中 `evidence_bundle` 保留完整段落。未来时段按下方专用路由；期间分析默认含本命条件包；择时需要本命解读时带 `include_natal_reading:true`。不为找 `ge_ju` 或 `yong_shen` 再跑诊断。
7. 完成本题解释：逐项核对盘面、原文条件、例外与范围。工具已标明不判的项目照说（见下「工具结论优先」）；其余根气、位置或救应需要判断时，写明这是按原文的推理、不是工具结论，并给依据。资料够用就完成解释，不能只列待查清单；确有缺项时说明影响哪条判断，并写出补全路径（缺什么资料、要核哪条原文或哪个工具字段），同时回答已能确认的部分。
8. 原局解读记录使用 `scripts/reading_support.py --stdin` 审核。未来入口的历法事实和两种行运例式已在各自计算中核查；不能塞进仅接受原局规则的审核器。临时补查按专用流程记录依据。成稿发出前用 `scripts/answer_check.py --answer - --facts <上一步的 .json>` 核对，正文从标准输入给（多个工具就重复 `--facts`；没存文件时才用 `--stdin` 传 `{"answer": 正文, "facts": [...]}`，不必读它的源码）：它机械核对引文是否在随包古籍里、四柱是否与盘一致、有无工具没给的分数、确定性断言、把未判格局说成定格、把并列说成唯一最好；facts 使用完整的实际成功工具结果，保留 ok、tool、version、候选与各人标签。有 error 先改再发，有 warning 时说明未核内容。工具结果带 `must_cover` 时（紫微运限四化要写各星落宫、合婚要写三元九宫的起宫、顺逆和步数、问格局要写还只是候选、出生时间贴近时辰交界要写两个时辰、六爻命中的条款有书内反例要两边写出处、装卦要逐爻写纳支六神六亲），每一项都要在正文同一行写出，漏一项报 error；正文里的段号不在本轮任何工具结果里时报 warning，先用 `classical_search.py --passage-id` 核实；只说「书里没有」而不写随包转录范围报 error；引古籍原文旁边既无书名也无段号、把注文（`layer=commentary`）说成原书正文，都报 error。它通过不等于语义正确，仍要核对正文是否忠实于记录。其他方法使用自己的原文和规则，不借八字来源 ID。
9. 先白话回答所问，短引文附在对应解释旁。个人择时可在八字背景之外，按事项和已核依据选择一种中国术数作为事件主法，说明选择理由与个人信息如何接入；不必让用户先懂方法名称。多法并列对照按明确要求展开，各自说明结果与分歧。

### 7.2 工具结论优先

v5.6 真实回答评测（`evals/v56/REPORT.md`）里，答错的主要原因是宿主在工具结果之外自己补结论。所以：

- 工具给了 `say` 句子（真太阳时比钟表多或少几分钟、未定柱在哪个钟表时段取哪个干支、年柱按立春分界、大运周岁与虚岁、请求当天的周岁、大运配法逐字判喜忌、格局只到候选、古籍检索不到只代表转录本、合婚按合冲刑害分组与日主互见），照抄这句，不自己把正负号改写成快慢、不重排候选对应、不把“忌”说成“未触犯”、不自己算年龄。合婚回答要包含 `pair_facts.say` 的“日主互见”一行。
- 工具写了「没判」「未接入」「给不出」「不判」，或几个选项等级相同、`first_choice` 为空，回答必须照说：说明并列、说明没判，不补判、不排先后。
- 大运 `conditional`、`mixed`、`partial` 分别表示条件未决、配法说法冲突、只有部分配法提到；都不能写成共同喜忌。`unresolved_conditions`、反向例外、`pending_actions` 必须保留；取运章已接入不代表配法或格局已成立。格局核对中的 `literal_state:met` 只说明字面条件齐备；`preserves_original` 与变化线索一起核，不能被首条命中覆盖。
- compact 大运的 `scenario_ref` 指向 `luck_index.scenarios`，干支的 `verdict_refs` 指向 `luck_index.verdicts`；读取引用才能看到完整条件、反例与具体未判原因，不能只看 `summary`。
- 干支、十神、生肖、旺衰、日期等级、大运喜忌只从工具输出取，不写 `python -c` 或其他代码自己另算。工具没给的就说没给。
- `--markdown` 草稿是正文骨架：改写成白话、调整顺序可以，不增删结论，保留出处。草稿末尾「写回答时」各条必须照做。
- 古籍照抄，不用省略号删掉会改变意思的部分；审校说明、工具白话不能当原文引。

### 7.3 白话输出

采用 Caveman 的简洁原则，清楚优先：默认约300–600字，使用最自然的日常白话，完整短句，一句一件事，保留原因、条件、否定和时间范围。

- 开头一至三句用普通话直答，让没学过术数的人也能独立看懂结论及限制。即使用户问“月令格局”，第一段也先解释哪些作用互相支持、哪些互相牵制，以及还不能确定什么；不要先给“杂气正官、透干有根、财伤俱透、救应未成”等标签再到后面翻译。默认最多三条主判断；要求详解时展开。
- 术语首次出现就解释，不能用另一串术语解释它。“透干”就是“这个字出现在天干一排”；“正官”先说明是相对于日主的一种克制关系，再谈本题作用，不能直接等同职业或性格。
- 每条按“白话结论 → 必要盘面 → 短原文与出处 → 紧跟白话解释”写成自然段。每段古文后解释它本来的意思、本人的哪些条件符合、为什么用于本题；现代场景解释单独标明。正文、注文、项目归纳分开，古文不占主体。
- 用户补充档期后的最终选择也要保留必要的短引文和白话解释；不能只剩一张排期表。若只支持现实排期，就解释所查古法的实际范围，不让原则性引文看起来认证了首选。
- 期间问题已返回原局条件包时，完成与本题有关的主要结构核查。不能只挑一条前提不符的例式，便当作整盘已经解释；说明能成立的关系、未成立的关系及各自原因。大运背景与这一周会发生什么分开回答。
- 说明已核实的结果，候选不当定论，模糊“可能”不能替代条件检查。
- 短期回答先核实每条解释的时间粒度。某一天对本人的吉凶按《协纪辨方书》相主（出生年干支）由 `fortune_reading.py` 给出，照它的等级和理由说；除此之外没有适用于本人的日、时条款，就不能把十神、冲合或重复出现的字改写成“周初宜整理、周末宜交付”“某日更适合沟通”等个人节奏；也不能合并成未经核准的整周主题。加上“象征、结构倾向、文化参考”不能补足依据。现代解读只能解释已成立的传统判断，不能替缺失的判断造结论。
- 建议依据已知现实处境，不从古代富贵、刑克直接推出现代职业或具体事件。
- 盘表放在直答之后，只列本题需要的项目；完整藏干、十神表按需展开。JSON、工程分数和审核日志留在工具结果中，文化参考性质说明一次即可。
- 用户要求保存或导出时，用同一次八字调用加 `--report <新路径.md或.html>` 保存核对报告；默认不落盘。HTML 可离线打开并展开原始资料，Markdown 便于继续核对。报告是工具事实与条件，不冒充宿主已完成的解释；保存失败按真实错误处理，不覆盖已有文件。懂术语的用户加 `--report-style professional`（四柱表、离线命盘图、条款核查表）；要发给别人看时加 `--report-redact`，生成隐去干支、出生日期时间地点、问题原话和公历年份的分享预览。用户要一张能发朋友圈的图时，加 `--card <新路径.svg>`（离线卡片：四柱、日主、月令、当前大运、条款与段号），给别人看加 `--card-redact`。
- 用户纠正时保留原判断和修订理由，不把已知经历计为预测命中。
