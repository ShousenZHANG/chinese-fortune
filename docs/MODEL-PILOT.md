# 3.0 模型输出试跑

本轮由当前正在运行的 Codex 协作 agent 实际读取技能、调用工具并撰写回答。精确模型型号未公开。它是一次开发中的宿主试跑，期间提示词和脚本均有变化：作者看过验收标准，30 例共用同一连续会话，没有调用外部模型，也不是同题旧版/新版盲评。

[原始记录](../evals/recordings/v3-agent-pilot.json) 保存 30 个原题回答、3 个本轮新增场景、实际命令参数、退出码、完整工具结果及摘要、来源和缺项。它也保留本次发现问题后的旧回答与修订，不能只看最新答案就把初次错误抹掉。

现已完成另一位协作 agent 的逐条评审：**原 30 题全部完成审核，六项标准下未发现剩余失败；21 题已回答、3 题部分回答、6 题等待输入。** 另 3 个补充场景均已回答并完成审核。具体依据见 [评审报告](MODEL-PILOT-REVIEW.md)。

回答作者没有自填评分，评审者是另一位 agent；但评审者参与过本版实现，因此这不是外部独立评审或盲测。R01 首轮相关性失败、R02 首轮盘面错误及后续修订均保留，不能称为首次运行全通过，也不能称为完成了 33 个完整个人解读。

## 本轮看到了什么

- 完整生日可以实际排盘，默认回答使用月令主线、盘面位置和可定位原文；没有把工程旺衰分数、神煞断语或旧调候首候选当成人生结论。
- 北京 1990-05-10 14:30 被识别为历史夏令时，真太阳时约 13:19；原局为庚午、辛巳、乙亥、癸未。当前所在地未提供，因此没有借用出生地或电脑时区生成流年。
- 未知时辰的首版回答曾固定乙亥日。最终入口检查了当日首尾时间后，发现日界可能变化，保留甲戌、乙亥两种候选。最新回答只固定年、月柱，不再指定日主；首版和修订理由都在 R02 的 `revisions` 中。
- 悉尼的夏令时空档和重复时间都触发错误，不生成默认成功盘。重复时刻另核得两次分别为 UTC+11 和 UTC+10，没有替用户挑选。
- 闰四月输入实际用 `--leap` 转换到 2020-06-11；因缺出生地点，仅完成历法核对，没有假装紫微整盘已完成。
- 引文示例实际定位到固定段落，正文和注文分开；原刻影像未核、旧调候表待核状态都如实回答。

这些观察只涉及本次输出和调用行为，不证明真实预测有效，也不等于已核定所有古籍规则。

## 原题与新约定的冲突

原 30 例没有一例明确给出现居城市。R01/R02 只有出生地；如果为了旧验收字段而默认现居地为北京，会违反新版时间约定。实际处理是先给出生资料能支持的原局，询问现居地，流年留空。

R03 只给经度，不能唯一确定法定时区。R06 指定钟表口径，但仍缺出生时区。R07 缺出生地点。R18、R20、R29 引用“刚才的判断”或“这张盘”，原题集并没有提供对应上文；回答没有编造历史消息。

最终评审将原题标为已回答 21 例、部分回答 3 例、等待输入 6 例。记录里的 `author_disposition` 保留作者早期分类，最终完成程度以 `review.disposition` 为准。对于缺项场景，“追问正确”不能包装成“已经完成个人解读”。

## 新增的三个时间场景

它们写在 `supplemental_runs`，明确由本轮设计，不冒充原有 30 题。每个场景都先真实运行 `request_time.py`，下游复用它返回的 UTC 时刻；没有用记录文件的宿主时间戳替代用户时间。

| 场景 | 实际调用时的结果 | 回答范围 |
|---|---|---|
| S01 北京出生、现居悉尼 | 悉尼 2026-09-06 14:38，UTC+10；出生盘按北京处理 | 己卯、丁丑、壬申、乙巳及月令透藏事实 |
| S02 现居纽约，按今天此刻起梅花卦 | 纽约 2026-09-06 00:38，UTC−4 | 山地剥，四爻动，变火地晋 |
| S03 现居悉尼，明确目标为上海未来时间 | 请求为悉尼 2026-09-06 14:38；目标为上海 2026-12-31 23:30，UTC+8 | 天泽履，上爻动，变兑为泽；说明午夜换日实现约定 |

S02/S03 采用年支序数、农历月日、时支序数，保留目标时间与请求时间两个字段，没有输出尚未核实的旺衰结论。当前 30 题审核命令不统计这些补充场景；评审者已另行逐条阅读并检查 3 条记录，均为已回答，具体依据见评审报告。


## R01 的真实失败与修订

另一位 agent /root/audit_release 指出首答的相关性不足：资料足够计算原局，却只说还需核查，把可以当轮完成的工作推迟了。初答和这条实际失败反馈分别保留在 R01 的 initial_text、initial_review，没有因为改好就删除。

随后本 agent 实际读取《子平真诠》的用神变化、成败救应、正官、偏官、伤官、合而不合、刑冲会合等完整章节，又补读强弱条款，按庚辛癸与巳藏丙庚戊逐项核对。新版回答说明哪些条件已成立、哪些没有成立、冲合次序在哪里仍有具体分歧，并把现代职业建议与传统结构分开。对应原文、盘面字段及尚未成立的条件写入证据包，结构审核通过；评审者重新通读相关章节后，将修订后的 R01 判为已回答，六项标准均通过，首轮失败仍保留。

本次失败也促使默认入口补充对应格局章节，技能要求资料够时当轮继续查条款。原有 29 个其他回答及 3 个补充回答并未在这轮偷偷重写，因此本记录属于多阶段开发试跑，不能当作整套 30 例在单一冻结版本上的成绩。

## 怎样复核

在源码目录运行：

```text
python -X utf8 evals/evaluate_readings.py --responses evals/recordings/v3-agent-pilot.json
```

评审完成后，该命令的实际结果为 `reviewed=30`、`errors=[]`、`pending=[]`，完成程度统计为 21/3/6。原始记录中的 `structural_evaluation` 保留的是评审前快照，当时尚缺 30 项语义审核，退出码为 1；它不表示当前仍未评审，也不能覆盖后来写入的真实 `review`。最新结果可重新运行命令复核，执行证据见评审报告。

R01、R02、S01 另实际执行了 `reading_support.py --stdin`，盘面和证据包结构检查均无错误；这不代替逐句审阅正文。

评审者应对照 `reading_input` 和最新工具结果审核正文。`chart` 保留诊断接口的实际结果，未知时辰可能仍含内部历法占位；正文只使用默认解读入口保留的确定事实。每条工具轨迹记录参数、退出码、结果及哈希。第二阶段重跑还记录了脚本内容哈希；prompt_stages 说明每阶段适用范围，保留早期 prompt_version 与当时命名的 final_prompt_version。后者不是发布冻结声明，不能把最新摘要追记成全程使用的版本。

评审时重点看：回答是否直接回应问题；普通人能否读懂；是否省略会改变意思的条件；古籍引文和层次是否一致；缺项是否真正影响计算；是否出现没有来源的现实事件、概率或精确日期。不要只查敏感词，也不要靠全部拒答获得高分。

本轮尚未做新旧版本盲评、多个独立宿主复跑、真实用户可读性测试或前瞻预测验证。它提供已审查的实际样本和保留的失败记录，作为下一轮冻结版本测试的依据。
